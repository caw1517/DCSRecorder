## Resolution: companion-owned associations; explicit revisions; bounded file verification

The user approved the association policy in the live discussion and subsequently operated DCS for the remaining checks. The bounded investigation is complete on DCS 2.9.29.27468. This resolves the decision, not production implementation or acceptance.

**Selected contract:** one authored mission may contain all seven aircraft. The companion owns persistent lineage and aircraft-association records plus immutable source/prepared revisions. IDs, names, copied markers, array positions and aircraft counts are correspondence hints, never historical identity proof. Confirm the intended aircraft once per changed revision; reuse that exact approved mapping afterward. Compatible additions retain prior mappings. Ambiguous/missing candidates block automatic preparation; incompatible authored placement or configuration refuses reuse. Saved scenes provide recovery. First recorded pose stays separate from authored spawn; do not translate the take. Legacy recordings do not acquire fabricated provenance.

**Observed editor evidence:** Save As/resaves, rename, additions, copy/paste, delete/recreate and group-container reordering were exercised. Custom unit/root fields were stripped; a nested archive marker survived. Delete/recreate reused IDs and names. A controlled four-to-seven comparison retained all original aircraft/group/route data exactly, and reversed group-container entries survived an editor save. Within-group leader/route/task ordering remains significant. Unknown differences require review rather than blanket normalization.

**Observed runtime boundary:** normal valid load matched; a separately loaded edited copy mismatched. Repacking identical mission data also mismatched exact bytes. After loading edited content, replacing its named archive with original bytes produced **MATCH / EDITED**: a successful file comparison can coexist with different loaded content. Fly Again retained original content despite replacement of the named archive. Unedited Mission Editor flight used the saved path; an unsaved briefing edit used `tempMission.miz` and mismatched. The edit was stored through a localization dictionary, so semantic comparison must resolve that indirection. After removing the diagnostic and restarting, DCS completed a load with zero diagnostic entries: plain DCS does not enforce this checker’s presence.

**Supported assurance:** source/prepared snapshot comparison and existing preparation/activation package verification. **No production runtime verification path is approved by this probe.** The new authored-mission implementation must require fresh approval bound to the loaded session, intended take and prepared revision, and refuse release when absent, stale, mismatched or unverified. A filename hash or existing tape token is insufficient. Loaded-content binding and fail-closed enforcement, including restart and replacement timing, remain acceptance requirements of [Complete Hornet mission setup and hot-start parking-to-parking playback](https://github.com/caw1517/DCSRecorder/issues/11). Initial archive checks cannot certify later scripted world changes or unobserved editor history; no universal tamper detection is promised.

Recovery: “This mission copy changed, or its identity could not be verified. Open the authored mission in Mission Editor, save it, and generate a new recording/playback copy in DCS Recorder. You can also use the scene saved with this take. The recorded flight has not been changed.”
